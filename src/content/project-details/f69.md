## The problem

Most feature-flag platforms evaluate centrally: your app calls a vendor endpoint with the user context, the vendor decides true/false, then you unblock the render. That works until the vendor is far away, slow, or down — and ~100 ms per decision is exactly the latency that causes UI flicker. f69 inverts the model: the manifest (rules, rollouts, segments) lives next to your code, and a small deterministic evaluator makes the call locally.

## How it works

- **Rust → WASM evaluator**: one evaluator implementation compiled to WebAssembly runs on edge runtimes — your edge worker, your server, or a CLI — and returns byte-for-byte identical answers everywhere.
- **Versioned manifest synced globally**: flags, rollouts, and segments ship to runtimes as a versioned manifest instead of being evaluated on a vendor's servers.
- **Two surfaces**: a dashboard (author flags, manage environments, mint service-account tokens — everything that changes workspace state) and an edge API (`POST /v1/identify`, `POST /v1/evaluate`) authenticated with service-account bearer tokens scoped to a single environment.
- **The evaluator is also a library**: SDKs can resolve flags fully offline with the same WASM core, so the offline and online paths physically cannot disagree.

## Decisions worth explaining

- **Deterministic over distributed**: a frozen bucket hash means a 10% rollout picks the same 10% on every runtime — predictable rollouts with zero coordination between edge nodes.
- **Fail-closed by default**: a malformed flag falls back to its declared default; one bad flag cannot break the rest of the fleet. Safety is the default path, not an option.
- **Three planes**: control (dashboard), logic (manifest), and edge (API). Keeping the runtime surface tiny and read-only makes it auditable — the edge never mutates state.
- **WASM as the portability layer**: one evaluator, every runtime. The same bet I keep making: compile once, run everywhere, stay fast.
- **Metering that matches usage**: billed on monthly tracked entities (MTEs), evaluations, and service accounts — with a real free tier (5k MTEs, 1M evaluations, 2 environments) and a usage-based Standard tier. Pricing is part of the design, not an afterthought.
- **Self-hosting is a documented path**: teams that can't send flag state to a third party can run it in their own infrastructure.

## Challenges & edge cases

- **The latency budget is the product**: the whole pitch is microsecond, local decisions — which forced the manifest + evaluator architecture instead of the conventional round-trip SaaS model.
- **Auth on the runtime surface**: service accounts scoped to a single environment, with the dashboard supporting passkeys for teams that need them.
- **Honest docs**: quickstart, core concepts (workspaces, environments, flags, segments, MTEs, evaluations), the rollout bucket contract, SDKs & API, and self-hosting are all documented as a real product — the site and docs run on Astro + Starlight, the stack I know best.

## What's next

The docs' roadmap shape is the product's shape: SDK coverage across more runtimes and growing the evaluation library. For me, f69 is the project where systems thinking — determinism, fail-closed defaults, metered billing — meets the edge.
